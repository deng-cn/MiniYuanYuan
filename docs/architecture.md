# 架构说明

这个项目有两代。第一代（`1124`，旧）走了一条弯路，第二代（`1125_jingjichang`，新）是现在开源的主体。
两代都列在这里，因为「为什么改成现在这样」比「现在是什么样」更有参考价值。

---

## 一、两代项目对照

| | 旧：1124 | 新：1125_jingjichang |
|---|---|---|
| 隐藏维 `d` | 480 | **384** |
| 计算层数 | 36（18 套 Attn × 2 遍微循环） | **12** |
| 注意力 | 12 头 / 3 KV，第 2 遍复用第 1 遍 KV | 12 头 / **2 KV**（标准 GQA，2:1 压缩） |
| FFN | qbilinear_B，**每 3 层共享** 1 组，共 12 组 | BiCrossGate，**每 2 层共享** 1 组，共 6 组 |
| FFN 中间维 | 960（2.0d） | 1152（**3.0d**） |
| MTP | 3（并行多 token 预测） | 0 |
| 唯一参数 | 24.87M | 19.71M |
| 训练轮次 | 1 epoch 跑完 + 第 2 轮 640 步 | 2 epoch 跑完 + MoE 第 3 轮 |
| 验证集 loss | 2.3267（ppl 10.24） | **1.8439**（第 2 轮）→ **1.7744**（第 3 轮 MoE） |
| 开源状态 | 只在此文档记录，**不发布权重** | 发布代码 + 权重 |

旧版为什么放弃：36 层里 18 套注意力跑两遍、每 3 层才有一组 FFN，等于把参数预算压在「深度」上而不是「容量」上。
跑完 1 epoch 后 val 2.3267，流畅度够了，但事实类问答 45 题只有 3 题能答对，逐字复现能力接近 0。
结论是这条路不值当，转去做更小、更宽、FFN 更密的 12 层版本。

## 二、第二代主线：12 层 BiCrossGate（19.71M）

### 2.1 整体形状

```
输入 token
  → Embedding (8302 × 384)
  → 12 × P4Block  [ RMSNorm → GQA(12Q/2KV, hd=32) → 残差 → RMSNorm → 共享 FFN → 残差 ]
  → RMSNorm → lm_head（与 Embedding 权重绑定）
```

- `max_position_embeddings = 1088`，RoPE `theta = 1e6`
- 无 dropout，pre-norm，RMSNorm eps `1e-6`
- 词表 8302（字词混合），`<unk>` 率 < 0.0002%

### 2.2 每 2 层共享一组 FFN

`ffn_share_group = 2`：L0/L1 用第 1 组，L2/L3 用第 2 组……L10/L11 用第 6 组。
注意共享的只是 FFN，**每层的注意力、两个 RMSNorm 都是独立的**。

这是本项目最核心的压缩手段。12 层独立 FFN 需要 12 组，共享后只要 6 组。

### 2.3 BiCrossGateFFN 怎么算

```python
q1, q2 = q(x).chunk(2)          # q: d → 2d，拆成两半
a = act1(q1 * x)                # 逐元素门控（默认 gelu）
c = act2(q2 * x)                # 逐元素门控（默认 silu）
gate = gate_proj(cat(a, c))     # 2d → i
return down_proj(gate * up_proj(x))   # i → d
```

参数量 `2d² + 4di`。对照标准 SwiGLU 的 `3di`：在 `i = 3d` 时，
BiCrossGate 是 `14d²`，SwiGLU 是 `9d²` —— 单组更贵，但只建 6 组，总量反而更省。

| 方案 | 组数 | 参数量 |
|---|---:|---:|
| 12 层各一组 SwiGLU（i=1152） | 12 | 15.93M |
| 12 层各一组 BiCrossGate（i=1152） | 12 | 24.77M |
| **每 2 层共享 BiCrossGate（i=1152）** | **6** | **12.39M** |

### 2.4 参数账（唯一参数，不含 tied 权重重复计数）

| 模块 | 计算 | 参数量 | 占比 |
|---|---|---:|---:|
| Embedding（与 lm_head 共享） | 8302 × 384 | 3,187,968 | 16.2% |
| Attention × 12 层 | 12 × (384×384 + 384×64×2 + 384×384) | 4,128,768 | 20.9% |
| **FFN × 6 组** | 6 × (2×384² + 4×384×1152) | **12,386,304** | **62.8%** |
| RMSNorm（12×2 + 1） | 25 × 384 | 9,600 | 0.05% |
| **合计** | | **19,712,640** | 100% |

FFN 是绝对大头（62.8%），所以「共享 FFN」这一刀切得最狠，也是后来想拆开的原因。

## 三、第三轮：MoE 稀疏热升级（30.34M 总参 / 23.26M 激活）

### 3.1 做了什么

保留第 2 轮全部权重，把 **Group 3（L6–L7）和 Group 4（L8–L9）** 两组 FFN 升级为 MoE：

- 每组一个**常驻共享专家**（`i = 1152`，等价于原来那组 BiCrossGate，权重直接继承）
- 每组 **6 个细粒度路由专家**（`i = 384`），Top-2 激活
- 共享组内**每层配独立路由器**（同组两层看到的路由输入不同）
- DeepSeek-V3 式**无辅助损失动态偏置均衡**（`bias_lr = 1e-3`，`clamp = 1.0`）

其余 4 组（L0–L5、L10–L11）保持原样，不稀疏化。

### 3.2 参数账

| | 参数量 |
|---|---:|
| 底座（第 2 轮） | 19,712,640 |
| 两组各新增 6 个专家 + 2 个 router | +10,626,840 |
| **合计** | **30,339,480** |
| 单 token 激活（Top-2） | 约 23.26M |

效果：val 1.8439 → **1.7744**，22 个语料分片留出验证集 CE 全部下降。

### 3.3 事后判断：这一步是误判

当时想解决的问题是「每 2 层共享一组 FFN，容量被压得太狠」。
正确的改法只有一个变量：**把 `ffn_share_group` 从 2 改成 1**，让 12 层各有一组独立 FFN。

| 方案 | 改动 | 参数量 | 变量数 |
|---|---|---:|---|
| **A. 拆开共享（本来该做的）** | `ffn_share_group: 2 → 1` | **32.10M** | **1** |
| B. MoE（实际做的） | 加 router + 6 专家 + 负载均衡 | 30.34M（激活 23.26M） | 4+ |

两者参数量几乎一样（32.10M vs 30.34M），但：

- A 只动一个配置项，结构、训练目标、优化器全不变，训完可以直接归因「就是容量变大了」
- B 同时引入路由、专家分配、负载均衡、稀疏梯度四套新机制，训完之后**没法回答**到底是谁带来的收益

MoE 版本身是有效的（1.7744 确实是三期里最好的），但它回答不了当初想问的问题，还额外换来一堆调参负担。
这是方法论上的错误，不是实现错误 —— 写在这里当反面教材。
